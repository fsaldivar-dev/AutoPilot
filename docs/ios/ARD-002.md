# ARD-002 — In-Process iOS Observer

Discovery + implementación (Fase 1 simulator, Fase 2 device físico) de un observer
TCP que corre **dentro del proceso del app iOS** y expone la accessibility tree
via JSON-RPC en `127.0.0.1:7002`. Entregable real: `libAutoPilotObserver.a`
linkeada con `-force_load`, sin XCTest, sin WebDriverAgent, sin entitlements
especiales.

## ⚠️ Dependencias críticas — leer antes de usar

Este observer **depende de 3 frameworks privados de iOS** cuya carga vía
`Bundle.load()` es lo que activa el subsistema de accesibilidad dentro del
proceso. Sin ellos el tree SwiftUI queda vacío.

| Path | Tipo | Riesgo |
|---|---|---|
| `/System/Library/AccessibilityBundles/UIKit.axbundle` | AX bundle | Apple puede mover/renombrar en cualquier release iOS |
| `/System/Library/PrivateFrameworks/AccessibilityUtilities.framework` | Private framework | Mismo riesgo |
| `/System/Library/PrivateFrameworks/AXRuntime.framework` | Private framework | Mismo riesgo |

### Implicaciones que NO se pueden ignorar

1. **🚨 No shippear a App Store con esta lib linkeada.** Apple rechaza
   automáticamente binarios que referencian APIs privadas. La lib **solo
   debe linkearse en builds de Debug/Development** (testing interno).
2. **Versiones iOS testeadas**: 26.1, 26.3. Versiones anteriores/posteriores
   no garantizadas — Apple puede cerrar estas APIs sin aviso.
3. **Kill-switch recomendado**: gatear con env var `AUTOPILOT_OBSERVER_ENABLED=1`
   o `OTHER_LDFLAGS[config=Debug]` para que el binario de producción jamás
   incluya la lib aunque el proyecto se compile con el mismo scheme.
4. **Plan B si Apple rompe las APIs**: caer a AX-macOS + XCUI (sim-only) —
   el fallback chain via `ActionRouter` (ARD-001) ya lo permite sin cambios
   de código. El observer se vuelve opcional; el resto de AutoPilot sigue
   funcionando.

### Dependencia externa adicional (device físico solamente)

- **`libimobiledevice` / `iproxy`** — necesario hoy para el túnel USB que
  conecta la Mac al socket del observer dentro del iPhone. Instalar con
  `brew install libimobiledevice`. **Fase 3 lo elimina** migrando a
  `xcrun devicectl` (incluido con Xcode, cero deps externas).

## Motivación original

AutoPilot opera desde fuera del proceso app (AX macOS para simulator, XCUI
runner via `autopilotd` para NavigationBar SwiftUI). Esto:

- Bloquea iPhone físico — AX macOS no penetra el framebuffer de un device real.
- Aplana SwiftUI en queries "fast" — AX macOS no ve compound buttons.
- Impone un ciclo daemon/runner pesado (`autopilotd`) para queries deep.

ARD-002 pretende resolver los tres moviendo la observación **adentro** del proceso.

## La fórmula ganadora (discovery del día)

**SwiftUI populate `_UIHostingView.accessibilityElements` perezosamente** —
solo cuando un cliente AX externo consulta. Desde dentro del proceso eso no
pasa automáticamente. Las 4 piezas que juntas lo resuelven:

1. **Cargar frameworks privados de AX** (idempotente, sin entitlements):
   ```swift
   Bundle(path: "/System/Library/AccessibilityBundles/UIKit.axbundle")?.load()
   Bundle(path: "/System/Library/PrivateFrameworks/AccessibilityUtilities.framework")?.load()
   Bundle(path: "/System/Library/PrivateFrameworks/AXRuntime.framework")?.load()
   ```
   El `+load` de esos frameworks registra el proceso como cliente AX.

2. **Post `UIAccessibility.post(.screenChanged, argument: nil)`** — notifica a
   SwiftUI que rebuild el árbol.

3. **Yield de main thread con `usleep(100_000)` desde background queue** — si
   el warmup corre en `DispatchQueue.main.sync`, el main thread queda bloqueado
   y la notificación no se procesa. Separar en dos `main.sync` separados por
   un `usleep` en background queue deja al main libre para construir el tree.

4. **Recursión en containers AccessibilityNode** — SwiftUI agrupa elementos
   relacionados (PIN pad, toolbar items, compound buttons) dentro de un
   container AccessibilityNode cuyo propio `accessibilityElements` contiene
   los hijos. Hay que recurrir en esos children, no solo en `UIView.subviews`.

El flujo final del handler `tree`:
```swift
DispatchQueue.main.sync { warmupAccessibility() }  // load bundles + post notification
usleep(100_000)                                     // yield main thread
DispatchQueue.main.sync { serialize() }             // walk + recurse
```

## Hallazgos empíricos

| Probada estrategia | Simulador | Device físico |
|---|---|---|
| `view.accessibilityElements` directo | nil hasta que AX externo query | nil perpetuo |
| `accessibilityElementCount()` directo | deadlock en `DispatchQueue.main.sync` | no probado (crash likely) |
| `UIAccessibility.post(.screenChanged)` solo | no despierta el tree | no despierta |
| `Bundle.load()` de UIKit.axbundle + AXRuntime + notification + yield | ✅ populated | ✅ populated |

| Intento que NO funciona | Por qué |
|---|---|
| `XCAXClient_iOS` (cargar el cliente XCUI) | Framework privado con entitlements — App Store rechaza |
| `UIApplication._accessibilityInit` | Selector existe pero no dispara el tree |
| `accessibilityActivate()` en SwiftUI node sin AX activado | Devuelve true silente, no ejecuta action |

## Device físico: setup

Pre-requisitos:
1. iPhone con Developer Mode ON + Trust this computer confirmado
2. Team ID configurado en el proyecto Xcode del app bajo prueba
3. `brew install libimobiledevice` para `iproxy` (spike — Fase 3 elimina dep)

Build:
```bash
cd libs/AutoPilotObserver && make device    # → build-device/libAutoPilotObserver.a
xcodebuild -project MyApp.xcodeproj -scheme MyApp \
  -destination "platform=iOS,id=$DEVICE_UDID" \
  OTHER_LDFLAGS="-force_load $(pwd)/build-device/libAutoPilotObserver.a" \
  -allowProvisioningUpdates build
```

Runtime:
```bash
xcrun devicectl device install app --device $UDID $APP
xcrun devicectl device process launch --device $UDID $BUNDLE_ID
iproxy 7002:7002 &             # USB TCP tunnel
auto tree                       # habla con el device via tunnel
```

## Limitaciones conocidas (Fase 2)

- **No synth touches**: `tap` usa `accessibilityActivate()` + `sendActions(.touchUpInside)`.
  Para elementos puramente gestuales (long-press context menus, pinch, custom
  gesture recognizers) el observer no puede dispararlos. Workaround: `tapAt`
  coordenada + hit test.
- **`tree deep` / XCUI-equivalente no migrado** — el observer ya ve el mismo
  contenido que XCUI deep, pero el comando `tree deep` sigue ruteando a
  `autopilotd` (que es sim-only). Decisión: unificar a `tree` en Fase 3.
- **`iproxy` es dependencia externa** — Fase 3 migrará a `xcrun devicectl`
  (ya incluido con Xcode) o implementación usbmux en Swift puro.
- **App se bloquea si iPhone se bloquea por auto-lock**: iOS mata procesos
  bajo block. Recomendación: Auto-Lock → Never durante tests.
- **`scroll` con target non-scrollable cae al fallback** que en device no existe
  (timeout 20s). Fix: retornar error más rápido.

## Invariantes de compatibilidad

1. Si `libAutoPilotObserver.a` **no** está linkeada en el app, `iOSDeviceResolver`
   detecta `probeSocket()` false y cae a AX+XCUI — backwards-compat garantizado.
2. `iOSDeviceResolver.simulatorBridge`, `xcuiBridge` siguen siendo `public let`.
3. `iOSAgentBridge` implementa `DeviceBridge` — métodos no soportados lanzan
   `BridgeError.unknown`, NO crashean.
4. `BuildInterceptor.build(args:)` sin cambios; `buildWithObserver(args:)` es
   método nuevo.
